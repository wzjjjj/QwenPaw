## Proposed Changes（将要产出的讲义与改动）

### A) 新增 Module 08：Channels 专题（3 课）

新增 3 个 Lesson 文件（命名跟随现有约定 `Module_08_Lesson_XX_*.md`），每课都包含：学习目标、关键问题、代码走读路线、关键节点入参/出参表、练习与验收清单。

1) `Module_08_Lesson_01_async_mentality_for_channels.md`
   - 目标：为不熟 asyncio 的读者建立最小心智模型（event loop / coroutine vs task / async generator / queue / thread-safe 回调）。
   - 结合 QwenPaw 具体代码点解释：
     - `ChannelManager.enqueue()` 为什么需要 `call_soon_threadsafe`（poll 线程 → 主 loop）
     - `WeixinChannel` 为什么用线程 + 自建 event loop（长轮询阻塞隔离）
   - 输出：用“图 + 术语对照表 + 3 个常见误区”降低阅读门槛。

2) `Module_08_Lesson_02_weixin_inbound_to_reply_end_to_end.md`
   - 目标：把“微信来一条消息”从平台到回包完整串起来，并对每个节点列：
     - 调用方（caller）
     - 被调方法（callee）
     - 入参（参数形状/关键字段）
     - 出参（返回值/副作用/产出对象）
   - 核心链路固定按实际代码：
     - `_poll_loop_async()` → `_on_message(msg, client)` → `self._enqueue(native)` →
       `ChannelManager.enqueue()` → `_enqueue_one()` → `_queue_manager.enqueue()` →
       `_consume_queue()` → `_process_batch()` → `BaseChannel._consume_one_request()` →
       `WeixinChannel.build_agent_request_from_native()` → `BaseChannel._run_process_loop()` →
       `BaseChannel.send_message_content()` → `WeixinChannel.send_content_parts()`
   - 重点解释 “native payload” 与 “AgentRequest” 的契约映射，以及 `meta`（context_token 等）如何影响回包。

3) `Module_08_Lesson_03_console_contrast_extension_and_tests.md`
   - 目标：用 Console 对比，解释 BaseChannel/ChannelManager 的抽象边界；并补齐“如何扩展新渠道”和“如何验证”。
   - 内容包含：
     - Console 的 `stream_one()` 为什么绕开 manager queue（更适合本地交互/打印）
     - 新渠道设计与“必须项”小节（按契约讲清必做/选做）：
       - **类与注册**：实现 `BaseChannel` 子类，设置类属性 `channel`；内置渠道走 `channels/registry.py` 的 `_BUILTIN_SPECS`，自定义渠道放到 `CUSTOM_CHANNELS_DIR` 由 `_discover_custom_channels()` 扫描 `obj.channel` 自动注册；如需额外 HTTP 入口，可在模块提供 `register_app_routes(app)` 且必须挂在 `/api/` 前缀下以避免被 SPA catch-all 吞掉。
       - **生命周期（必做）**：`start()`/`stop()`，负责启动接收（webhook/WS/long-poll 线程等）与资源回收；若有后台线程或自建 event loop，必须能在 `stop()` 里收敛。
       - **入站适配（必做）**：`build_agent_request_from_native(native_payload)`，把平台消息解析为 runtime `content_parts`，计算 `session_id`，并用 `build_agent_request_from_user_content(...)` 生成 `AgentRequest`；必须确保 `request.channel_meta` 携带回包所需字段（例如 webhook、context_token、receive_id 等）。
       - **出站发送（必做）**：`send(to_handle, text, meta)` 最小可用；推荐覆盖 `send_content_parts(to_handle, parts, meta)` 以支持图片/文件/视频等原生发送（否则会退化为文本拼接 `[Image: ...]`）。
       - **队列模式（必做决策）**：默认 `uses_manager_queue=True` 让 `ChannelManager` 负责“按 session 串行 + 批量合并”；只有确有必要（例如纯本地交互打印）才考虑绕开 manager queue 并自定义 consume 路径。
       - **会话与路由（强烈建议）**：实现/覆盖 `resolve_session_id`、`get_to_handle_from_request`、`to_handle_from_target`，把“同一会话串行”和“主动推送目标”定义清楚（尤其群聊/私聊隔离策略）。
       - **可观测性（建议）**：实现 `health_check()`，必要时实现 `doctor_connectivity_notes()`，以便 `doctor` 或控制台能看到渠道健康与依赖可达性。
     - 测试与契约：
       - 参考 `tests/unit/channels/` 与 `tests/contract/channels/` 里现有模式，讲清如何写最小回归用例（不要求新增测试，但给出可操作步骤）。
     - 选读：Cron/Heartbeat 如何通过 `channel_manager` 分发事件（作为渠道模块的“使用方”视角，帮助理解接口契约；点到为止）。
